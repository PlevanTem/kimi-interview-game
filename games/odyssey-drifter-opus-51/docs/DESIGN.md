# 设计说明：为什么是这些选择

这份文件记录本次重制的判断依据、被推翻的方案，以及仍然可能是错的地方。
玩法的规范定义在 `context/gameplay-spec.md`；这里只写理由。

---

## 1. 起点：旧版为什么被退回

旧版 `odyssey-drifter` 的 Gate 2 被用户直测退回，原因是**连线意义、通关规则与环境因果不可读**。
这三条都不是美术问题，是"玩家看不到自己在做什么、为什么失败"的问题。

所以本次重制的第一原则是：**每一条判定都必须在做决定之前就画在屏幕上**。

具体落实：

- 承重容量、负载、断裂位置在**松开之前**就以起毛纤维和叉号画在草稿上。
- 可以起手的光头永远在发光，不需要猜。
- 释放窗口用一个持续收缩、在拍点闭合的环表示，而不是一行文字。
- 失败原因写进回溯画面（"坠落 · 时间与光线一并收回"）。

## 2. 为什么"手势就是那条线"

立项报告里的核心句是"以一次按住—移动—松开的连续动作驭使承重光线"。
有两种实现方式：

- **A：玩家选择一条参数化弧线**（拖动控制点）。容易调平衡，但手感是"调参数"。
- **B：玩家指针走过的路径本身成为那条线**。难平衡，但手感是"我写了一笔"。

选 B。理由：报告里"可传播性"的论据是"玩家手势实时留下独一无二的运动轨迹"，
A 做不到这一点——所有人的线看起来都一样。B 还顺带解决了"张力"的定义问题：
弦长 / 弧长是一个玩家用手就能直接感觉到的量，绕得越远越松。

代价是必须处理采样噪声（重采样 74 点 + 两次保端点平滑）和光量预算
（否则最优策略是画一条无限长的松线）。

## 3. 速度只有一个来源

阿迦在线上的加速度只来自切向斜率。没有"冲刺键"，没有"线的类型"。

这带来一个免费的、玩家能自己发现的结论：**末端向上翘的线是弹射器**。
它不是一条特例规则，是同一条公式的结果——所以玩家学会一次就能到处用。
同理，中间下凹的线会先加速再减速，可以用来"接住"一次高落差。

## 4. 同步窗口挂在脚步上，不是挂在断口上

第一版把释放窗口定义成"距离断口 0.34 秒"。问题很明显：玩家通常提前很久就画好了线，
几乎不可能命中，同步变成一个装饰性数字。

改成挂在**脚步拍**上：预读期间每一次落脚都是一次机会，±145ms 命中即算。
阿迦的脚尖两拍就是"窗口开了"的提示。这样同步从"运气"变成"跟着他的节奏"，
也让"NPC 是动作系统的另一半"这句话第一次有了具体含义。

## 5. 回溯必须留出助跑

第一次实现只要求恢复点"合法"，结果是自动驾驶跑到第 2 跨就无限循环：
玩家被丢回断口边缘，没有时间画线，立刻再坠落。

现在的规则是三条同时满足：合法着地、距坠落 ≥0.9 秒、**剩余助跑 ≥1.1 秒**。
另加一条兜底：同一断口连续三次失稳，退回上一处停息台，光量全满，缓冲清空。

这是本次重制里最有价值的一条修正，而且它不是靠"感觉"发现的，是自动驾驶跑出来的。

## 6. 落地要吸收速度

短平台（尤其是回声桥群的慢路）在高速落地后只剩不到半秒反应时间。
现在落到平台上时速度上限 248 px/s，且平台上的回稳系数是线上的 2.3 倍。

设计立场：**平台是读取世界的地方，不是冲刺跑道**。紧线的奖励应该是"跨得过去"，
不是"在平地上跑得更快"。

## 7. 分叉不用图结构

回声桥群的"快而紧 / 慢而有记忆"两条路线，不需要任何路径图或节点连接。
两块平台同时存在于同一个断口里，玩家的线落到哪块就走哪块，之后各自向右跑。

唯一的约束是几何：慢路必须完整落在断口内部，并留出回到主路的横向余量。
第一版没有这条约束，慢路会横向压住主路，把"二选一"变成"唯一一条走不通的路"。

## 8. 全部程序化的代价与收益

**收益**：零资产文件、无限长的城市、确定性种子、Gate 3 之前完全合规、
视觉与玩法共用同一套数据（平台的呼吸位移既是画面也是碰撞）。

**代价**：填充率。五层城市 + 辉光缓冲 + 描边叠加在低端 GPU 上可能吃满。
已做的缓解：半分辨率辉光、三档画质、视口裁剪、窗光只在少数楼层生成。
未做的验证：真实低端机型的 p95 帧时间。

## 8.5 教程为什么要用真规则跑

最省事的做法是录一段视频，或者给教程写一套"一定会成功"的简化逻辑。两种都不做。

- **录像会过期。** 任何一次平衡改动都会让视频和游戏对不上，而没人会记得重录。
- **简化逻辑会说谎。** 教程里成立的东西，玩家上手时不成立，这正是旧版被退回的那类问题。

所以 `demo.js` 只做三件事：把指针放到哪、什么时候按下、什么时候松开。
判定、承载、断裂、回溯全部由游戏本体给出。代价是演示有可能"演砸"——
但那恰好是第 5 步想要的：让它真的断一次。

为此加了一个自适应步骤：如果计划中的过载线顺路借到了锚点、`load` 没越过 1，
演示会按实际读数继续把线拉长，直到真的过载。**演示不允许假装失败，也不允许假装成功。**

## 9. 我仍然可能错的地方

- **同步窗口 ±145ms 可能太宽**。自动驾驶 23 跨拿到 22 次同步，最长链 18。
  对机器来说这说明窗口存在；对人来说可能意味着"随便松手都算同步"，
  那样同步就失去了意义。这需要用户本人试玩才能判断，我不打算自己调。
- **慢路可能不值得绕**。它给记忆物和一个锚点，但要多画一条线。
  如果玩家发现直路永远更优，"有意义的选择"这根支柱就是假的。
- **玩家关注的是"线"还是"人"**。立项报告明确要求 Gate 2 分开记录这两种反馈，
  不要混成一个平均分。本版把两者绑得很紧（同步挂在他的脚步上），
  这可能掩盖住"其实玩家只关心画线"这个结论。
- **4–6 分钟是否足够**。自动驾驶用 174 秒跑完，因为它从不犹豫。
  人类会更慢，但也可能因此觉得中段重复。
- **演示是否反而降低了发现感**。把"手势就是那条线"直接演出来，
  可能让玩家少了自己试出来的那一下。所以演示是可选入口，不是开场强制流程。

## 10. 停止条件（沿用立项报告 §17）

满足任一项就回到玩法规格，而不是继续叠加系统：

- 用户在两轮迭代后仍不认为驭线是一次连续动作。
- 用户认为失败主要来自延迟、随机或不透明判定。
- 用户只能盯 HUD，无法从阿迦身体获得有效信息。
- 需要自动路线吸附、自动释放或隐藏容错才能通过。
- 目标设备 p95 帧时间持续超过 20ms。
